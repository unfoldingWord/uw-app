# A web render harness over the memory adapters

The sim proves behaviour but renders nothing, and the agents that build the app have no phone, so until 2026-09-29 no screen had been seen before a device run. `npm run shots` exports the real app with `expo export --platform web` and photographs every screen in Chromium, in light, dark, reduced blur, right to left, Urdu, Hindi and large text, at 360 px. It is QA only; there is no web product. On web Metro picks `src/platform/ports.web.ts`, a one-line re-export of `@sim/web/ports`, which builds the Ports from the sim's memory adapters, restores a device image the sim fixture world wrote in Node, and makes Files, Kv, Db and Http wait for that image before their first call. We decided that these wrappers, with the sim's pinned Clock and Ids, are decorators over the memory adapters and not a third adapter set: no port gains a web adapter, the port contract cases still run against exactly two adapters, and the harness shows what the memory adapters hold, nothing more. The harness renders the drafted locales through the `drafts` locale gate; the native app keeps the release gate. What keeps this from leaking is a check, not care: `npm run bundle`, the last step of `npm run verify`, exports the iOS and Android bundles with source maps and fails on any module from `sim/`, `scripts/`, sql.js or react-native-web, and it has been observed red. The cost is five dev dependencies, a CSS branch in `backgroundImage` for the aurora and wells, and a harness whose pictures are a browser's rendering of React Native Web rather than a phone's: blur, fonts and hit areas are close but not native, so the device CI (Maestro on an emulator and a simulator) and a recorded phone run remain the evidence for glass rendering. Accepted in issue #7; proposal `docs/proposals/2026-09-30-web-render-harness.md`.
