# Performance comes from tuning the current codebase and moving measured hot paths native

Leaders reported that the app feels slow, and the product owner asked on issue #100 whether to rewrite in native code or tune the current codebase, and whether a setup exists that keeps app logic in one place with native code on both platforms. The current shape already is that setup: one TypeScript kernel (ADR 0001) serves Android, iOS and the Node sim; React Native renders native views on both platforms; and local Expo modules move measured hot paths into Kotlin and Swift behind a port, with a memory adapter so the sim keeps working (`modules/uw-archive` halved the English download wait on the iOS simulator, 94 s to 46 s). Accepted on 2026-11-05 through `docs/proposals/2026-11-05-performance-strategy.md` (decision 101): measure on a low-end Android phone and an older iPhone first (#46), then fix by measurement, in order: rendering (virtualised lists and no per-row blur, #85 and #38), release builds (R8 and resource shrinking, phone-only CPU types for sideloaded APKs, set per EAS profile because the device CI's emulator needs x86_64), work off the JavaScript thread (yielding and batching first, then a separate JavaScript runtime or a local native module behind a port), and visible feedback on every action (#99). Rejected: a native rewrite in Kotlin and Swift (two copies of every rule and the loss of the sim, replay and the checks), and Kotlin Multiplatform or Flutter (a full rewrite to reach the current state), because no measurement shows React Native itself is the cost. The cost of this choice is that no phone timing exists yet, so the first work is measurement, not code.
