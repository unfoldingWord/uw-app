# Preference-shaped owners live in the kernel

The scaffold placed bookmarks, preferences and the invitation schedule in feature `store.ts` files, one writer each. That shape could not work: a feature service sees only the kernel, so a feature store has no port to write through and cannot emit an event, and every one of these values is read or written by several features, which may not import each other (the content language by Home, Study, Formation and Languages; the locale by every screen; bookmarks by Study and Home). The invitation also needs the Locale and Http ports. We decided that three kernel modules own them: `preferences` (the closed list of preference keys and the last passage per language), `bookmarks` (the `bookmarks` table) and `partners` (the invitation schedule, the cached impact stories and their images under `partners/`). Each has an `owns` export, one writer, `redo` handlers for replay and a snapshot that identifies no one, and each journals its changes (`PreferenceChanged`, `BookmarkAdded`, the invitation events). A new durable value therefore goes to the kernel module that owns its kind; a feature `store.ts` remains a reserved filename the `owns` check walks, for a value one feature alone reads and writes once a store can reach a port, and none exists today. The cost is a larger kernel (thirteen modules) and that preference-shaped work is a kernel change, reviewed as such. Accepted in issue #6; proposal `docs/proposals/2026-09-29-preference-owners-in-the-kernel.md`.
